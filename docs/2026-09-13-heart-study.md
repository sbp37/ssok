# 하트 패드 재질·WebP 비즈 실험

기준 main `02fefe1`, 별도 브랜치 `codex/heart-material`. 기존 미커밋 변경 없음 확인 후 시작.
이번 범위는 하트 한 종류다. 다른 패드의 재질·개수와 손맛 상태기계, 수집통 물리, 저장·보상·광고 정책은 변경하지 않았다.

## 변경

- `pads/PadTypes.ts`, `beads/Bead.ts`: 하트 표면 목표 16개(기존 전역 0.7 배율 포함), 표면 비즈 반경 1.28배. 실제 배치·판정 반경도 함께 커진다. 큰 물체부터 충돌 없이 배치하므로 실제 개수는 공간에 따라 줄어들 수 있다. 기존 아래층·왕비즈·보물 추첨을 유지한다.
- `gel/Material.ts`, `gel/Gel.ts`: 하트만 밀키 핑크로 조정. 여러 겹 외곽 선 대신 실제 윤곽으로 계산한 시각용 높이와 넓은 반광, 두께 있는 옆면. 이미지에 그려진 구멍을 패드에 덮지 않는다. 하트/별 빈 홈도 둥글게 이완한다.
- `beads/BeadSprites.ts`: 하트 비즈 윤곽에서 거리장을 구해 둥근 안쪽 벽/어깨의 조명을 캐시한다. 비즈 원본을 흐리게 하지 않고 거리장만 완만하게 하여 픽셀 계단이 조명 떨림으로 증폭되지 않게 한다. 실제 3D 메시/굴절 시뮬레이션이 아닌 시각적 근사다.
- `beads/BeadAssets.ts`: 개별 생성한 유리·진주·하트 레진 WebP 3개 연결. 사전 로드/디코드/캐시, 실패 시 기존 사진→절차적 렌더러. 상세 정보는 [원본·크롭·크기 표](../art/beads/heart-study/README.md).
- `Game.ts`, `collector/Collector.ts`: 하트에서 생성된 비즈에 art 구분을 유지하여 뽑힌 뒤에도 같은 이미지로 수집된다. 늘어나는 목은 하트에서만 35% 더 도톰하게 그린다. POP 거리·힘·스프링·이동/충돌 수식은 그대로다.

원본 PNG는 `art/beads/heart-study/`, 배포는 `public/assets/beads/studio-*.webp`(합계 60,062바이트).
원본 3개 모두 실제 알파가 있고 이웃 물체나 바닥 그림자는 없다. 참조 하트 패드 그림 자체는 배포 에셋으로 쓰지 않았다.

## 검증

- `pnpm run typecheck`, `pnpm run build`, `git diff --check` 통과. 55모듈, JS 317.35kB / gzip 103.03kB. lockfile/새 패키지 변경 없음.
- macOS 데스크톱 Chrome에서 360/390/430×844 기준 전후 캡처. 개발 브라우저에서만 고정 RNG 517 사용, 운영 생성에 시드 파라미터를 추가하지 않음.
- 390px / DPR 2: 실제 포인터로 표면 비즈 잡기→POP→수집, 아래층 발견, 병 정착 확인. 비교 배치는 표면 16 + 아래층 10 = 26개. 병 수집 14개, 보물함 경로 2개, 이후 잡을 수 있는 비즈 10개. 희귀 비즈는 병이 아닌 보물함 경로를 따르므로 병 개수를 전체 POP 개수로 보지 않는다. 새 비즈 art 유지, 실행 예외 0. 새로고침 전후 localStorage 동일.
- 스튜디오 WebP 3개 로딩 실패 시 기존 사진으로, 모든 비즈 이미지 실패 + WebGL 비활성화 시 Canvas 절차 렌더러로 각 1개 잡기→수집 성공. 실행 예외 0, 가로 넘침 없음.
- 증거: 작업공간 `output/playwright/rim-audio/heart-before-{360,390,430}.png`, `heart-final-{360,390,430}.png`, `heart-dpr2-*.png`, `heart-video/*.webm`.

100개 개발 시드 배치 검사(deeperChance=.4, kingChance=.3, 숨은 보물 별도 지정 없음): 표면 15~16개, 전체 17~28개. 운영에서는 기존 숨은 보물과 깊은층 확률이 적용되어 범위가 달라질 수 있다.

Chrome 152 / macOS / 390px / DPR 2, 로컬 Vite 개발 서버에서 180회 update+render CPU 제출 시간: 중앙값 0.30ms, p95 7.60ms, 최대 25.40ms. GPU 완료 시간/실제 rAF 간격이나 모바일 FPS 측정은 아니다. WebP 응답 크기 합 60,062B, 로컬 요청 15.5~17.5ms(다운로드와 디코드 전체를 보장하는 지표가 아님). 동일 조건의 변경 전 CPU 측정은 없으므로 빨라졌다고 주장하지 않는다.

실기기 안드로이드/토스 WebView 검증은 아니며 모바일 60fps를 보장하지 않는다. 전체 앱/아이콘/토스 등록을 대체하는 새 게임이 아니라 현재 게임의 하트 실험이다. main 머지·푸시·운영 배포는 아직 하지 않았다.
